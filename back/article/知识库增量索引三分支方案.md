# 知识库存储与索引优化方案

> 状态：方案待落地。  
> 范围：增量决策、切块、切块去噪、召回分数阈值；Ask 编排本身不改，但阈值会影响送给 LLM 的材料。

本文约定已认同的优化点，每个点只写清：**现状是什么 → 打算怎么优化**。

---

## 优化点 1：重嵌规则与元数据更新

索引时要回答：**这篇文档这次要不要动、动到什么程度？**

### 现状

```text
同路径 + 正文 content_hash 相同 + 已 indexed → 整篇跳过
否则 → 删旧向量 → 重新切块 Embedding → 写入（全量重嵌）
```

| 实际变化 | 现在会怎样 | 问题 |
|----------|------------|------|
| 正文变了 | 全量重嵌 | 正确 |
| 只改标题或更新时间 | **整篇跳过** | SQL / Chroma 的 title、updated_at 仍是旧值，按标题/时间过滤不准 |
| 换了 Embedding 模型 | **整篇跳过** | 新旧向量混库，相似度不可比 |

只认「正文有没有变」，不认元数据与模型变化。

### 打算怎么优化

拆成三种动作：

| 动作 | 什么时候 | 做什么 |
|------|----------|--------|
| **完全跳过** | 正文、标题、更新时间、模型都没变 | 不动 |
| **只更新元数据** | 正文和模型没变，标题或更新时间变了 | 更新 SQL 与 Chroma 的 title / updated_at；**不重算向量** |
| **全量重嵌** | 新文件 / 正文变了 / 换了模型 / 强制重建 | 删旧 → 切块 → Embedding → 写入 |

一句话：向量过期 → 重嵌；只有过滤字段过期 → 刷元数据；都没过期 → 跳过。

## 优化点 2：长文本切块按标点，不按字数硬切

### 现状

先按空行分段，短段合并；**超过 `chunk_size` 的长段再按固定字符窗口硬切**（带 overlap）。  
长句、长段容易从句子中间断开，单块语义不完整，向量检索更难对准「一整句/一层意思」。

### 打算怎么优化

超长段优先在 **句号、问号、叹号等标点**（如 `。！？；` 及对应英文标点）附近切开，尽量保持句子完整。  
仍可保留长度上限：找不到合适标点时，再退回字数切分作为兜底。

目标：块边界对齐自然语言，而不是对齐字符计数。

## 优化点 3：切块后对块内容去噪（待探讨）

### 现状

切出的 chunk 基本是原文片段，**没有单独的去噪步骤**。  
日记/Markdown 里常见的日期行、重复标题、无意义符号、过短碎片等，可能直接进 Embedding，稀释语义、干扰召回。

### 打算怎么优化

在切块完成、写入向量库之前，增加一步「块级去噪」。  
**具体规则待探讨**，例如可讨论：

- 去掉或弱化哪些噪声（纯日期行、连续空白、重复页眉等）  
- 过短块是丢弃、合并，还是保留  
- 去噪是否改变 `content_hash` / 是否触发重嵌  

本点先立项，实施方案另定后再落地。

## 优化点 4：Top-K 召回增加相关度阈值

### 现状

向量检索按相似度取 Top-K，**只要进了前 K 名就会返回**，没有「够不够像」的下限。  
库不大或问题偏题时，排名靠后的命中相关度可能很低，仍会进入结果列表；走 Ask 时这些低匹配片段会一并送给 LLM，容易干扰回答、甚至带偏结论。

### 打算怎么优化

在 Top-K 之后增加一步：**按相关度分数（或距离）设阈值，低于阈值的命中直接丢掉**。  
仍先取 Top-K，再过滤；宁可少几条高质量材料，也不把明显不相关的内容塞给 LLM。

阈值具体数值可配置，上线后按实际命中分布再调。
