# 作品集扩展与打磨

## 可选扩展（P2，稳定演示后再做）

1. 对话历史 / 多轮上下文
2. 检索调试面板（各路命中、RRF、rerank 分数）
3. 简单权限或多知识库切换

## 面试问题处理关键点

1. 流式输出前端怎么做？断线、重试、取消怎么处理？
2. RAG 为何要混合检索？Rerank 开/关有何差别？
3. 幻觉怎么减？前端能做什么（引用、拒答、加载态）？
4. Cursor 提效后，你怎么保证代码质量和可维护？

## 求职打磨清单

目标：把「能跑的工程」打磨成「能稳定演示、能讲清价值」的作品集。  
已有底盘：混合检索 + LangGraph 编排 + SSE 流式前端 + 技术文章。缺的不是再堆功能，而是演示、溯源、可观测、效果对比。

### 已有亮点（别丢）

| 已有能力 | 面试怎么卖 |
|----------|------------|
| 向量 + FTS + RRF + Rerank | 「做过完整召回漏斗，不是调个 Chat API」 |
| LangGraph：rewrite → retrieve → answer | 「懂 Agent 编排，不是只会接流」 |
| 前端 SSE 逐步展示检索过程 | 「AI 产品前端，过程可观测」 |
| 增量索引三分支 | 「懂知识库工程，不是一次性导入 Demo」 |
| 系列技术文章 | 「能沉淀方案，适合分享/带人」 |

### P0｜没有这些，很难叫「作品集」

- [ ] **稳定演示包**：5 个必答问题 + 1 个拒答/空结果问题，次次可复现
- [ ] **5 分钟录屏 + 口述稿**：背景 → 架构 → 难点 → 效果
- [ ] **根目录演示 README**：启动、账号、预热、演示步骤
- [ ] **回答引用**：最终答案下挂来源（标题/路径/片段），证明可溯源
- [ ] **空结果与失败体验**：无命中、LLM 失败、取消、超时，都有明确 UI，不白屏
- [ ] **简历项目条目**：1 段话写清负责前端/检索/编排哪几块，含技术关键词

### P1｜有了这些，开始像「可交付产品」

- [ ] **检索调试面板**：同屏对比 vector / keyword / RRF / rerank 的命中与分数
- [ ] **效果对比实验**：开/关混合、开/关 Rerank，用固定问题集记更好/更差案例（表格即可）
- [ ] **知识库状态页**：已索引文档数、chunk 数、最近索引时间
- [ ] **示例问题按钮**：一键提问，降低演示失误
- [ ] **文章挂到作品入口**：混合检索 / Ask 编排 / 增量索引，作为设计说明

### P2｜加分，但别抢 P0/P1 时间

- [ ] 多轮对话（带上下文摘要或最近 N 轮）
- [ ] 简单评测脚本（命中率/人工打分，哪怕 20 条题）
- [ ] 文档列表管理（查看/删除/重建索引）
- [ ] 基础观测：ask_logs 前端查看、耗时展示
- [ ] Docker 一键起（方便别人复现）

### 可以先不做（投入产出低）

- 多租户/复杂权限、微调大模型、换一堆新框架、重做炫酷视觉
- 再开第二个无关大项目

## 做的过程中要深耕的点

深耕 = 真懂、能讲、能改，不是调参碰运气。

### 1. AI 产品前端（主战场）

- SSE 流式协议、分帧解析、Abort、中途失败、登录过期刷新
- 对话态：stage / step / hits / answer 如何映射成 UI
- 可观测交互：让用户看见系统在干什么

对应面试：流式/取消、幻觉与前端、Cursor 与质量。  
产出物：AskChatWidget 成为能逐行讲解的代表作。

### 2. RAG 漏斗原理（能讲即可，不必转算法岗）

- 为何混合：语义 vs 字面各自解决什么
- RRF 为何比硬拼分数合理
- Rerank 开/关对召回与延迟的取舍

产出物：调试面板 + 一张对比表 + 能口述 3 分钟。

### 3. 工程闭环与质量（拉开和「Cursor 堆代码」的差距）

- 索引一致性：documents / chunks / FTS / Chroma 不同步会怎样
- 关键路径与降级：检索空、改写失败、LLM 挂了怎么办
- 用测试锁住关键路径

产出物：测试 + README「已知限制/降级策略」一节。

### 4. 业务表达

- 30 秒定位：不是 ChatGPT 套壳，是「私有知识可溯源问答」
- 用指标说话：延迟体感、命中案例、开关对比（手工统计也行）

产出物：录屏旁白 + 简历 bullet。

### 5. 适度懂后端编排（够用即可）

- LangGraph 三节点输入输出、SSE 事件从哪来
- 配置项如何影响行为（fetch/候选/top_k/rerank）

不必深耕：模型训练、分布式向量库集群、复杂 Multi-Agent。

## 建议节奏（8 周）

| 周次 | 做什么 | 深耕点 |
|------|--------|--------|
| 1–2 | P0：演示包、引用、失败态、录屏 README | 前端 SSE + 体验 |
| 3–4 | P1：调试面板 + 开关对比表 | RAG 原理讲清楚 |
| 5–6 | 补测试、降级说明、文章入口整理 | 工程质量叙事 |
| 7–8 | 模拟面试 + 改简历 + 按反馈补一小刀 | 表达与取舍 |

2. 写演示脚本 + 启动说明

## 现有 RAG 作品还需优化什么

结论：链路骨架已完整（混合检索 + 编排 + SSE）。要优化的不是再加召回路，而是 **效果可感知、失败可控、过程可解释**。

### 1. 效果层（最该先动）

| 问题 | 现状 | 优化方向 |
|------|------|----------|
| 语料太薄 | 几篇友情类短文，约十来条 chunk | 扩到 20～50 篇、主题略多样；否则再调参也像玩具库 |
| 召回窗口偏紧 | `fetch_k=5` / `candidate_k=5` / `top_k=2` | 小库可先 `fetch_k=8~10`，精排仍截 2～3；用固定题集对比 |
| 空命中仍去生成 | 检索为空也会进 `answer` | hits=0 时短路：直接「知识库未覆盖」，不调 LLM |
| 低相关未拒答 | 有 rerank 分，但没用阈值拦截 | 精排分过低时拒答或提示「依据不足」 |
| 无效果对照 | 混合/Rerank 只能改环境变量 | 做开关对比表（或请求级开关），证明混合/精排有用 |

勾选：

- [ ] 扩充并整理演示语料 + 5 必答 / 1 拒答题
- [ ] 空命中短路，不调用 LLM
- [ ] 低相关拒答（基于精排分阈值）
- [ ] 调整/对比 fetch_k、candidate_k、top_k
- [ ] 开/关混合、Rerank 的效果记录表

### 2. 可解释性（作品集 + 调参都靠它）

| 问题 | 现状 | 优化方向 |
|------|------|----------|
| 中间分被丢掉 | `_public_hits` 丢掉 `vector_rank` / `bm25` / `rrf_score` | 调试接口或 SSE 里保留这些字段 |
| 前端只见过程标题 | 有逐步事件，但难并排对比 | 检索调试面板：四路命中 + 分数 |
| 答案缺结构化引用 | Prompt 让模型自己写来源 | 最终回答下挂 `retrieve_done.hits`（标题/路径/片段） |

勾选：

- [ ] `_public_hits` / SSE 保留 rank 与各路分数
- [ ] 检索调试面板（或 search 返回分项分数）
- [ ] 最终回答挂结构化引用来源

### 3. 入库与一致性

| 问题 | 现状 | 优化方向 |
|------|------|----------|
| 切块策略偏简单 | 段落后按固定字数硬切（300/50） | 对标题/列表更友好；或按文档类型调 `chunk_size` |
| 四库一致性靠自觉 | 索引逻辑有，但缺健康检查 | 检查 SQL chunk 数 vs FTS vs Chroma；不一致可一键 backfill |
| 文档管理弱 | 能上传索引，缺列表/删除/状态 | 至少：文档列表、chunk 数、最近索引时间 |

勾选：

- [ ] 索引健康检查接口/脚本
- [ ] FTS `backfill_from_chunks` 入口可触发
- [ ] 文档列表与索引状态展示
- [ ] （可选）优化切块策略

### 4. Ask 链路体验（影响观感）

| 问题 | 现状 | 优化方向 |
|------|------|----------|
| 改写可能伤关键字路 | 改写后的问句同时喂向量和 FTS | 小实验：关键字路用原问句、向量路用改写 |
| 冷启动慢 | Embedding/Rerank 首次加载重 | 启动预热或演示前 warmup |
| 失败态不完整 | 有取消/部分 error | 补：超时、无命中、LLM key 缺失的友好文案 |
| 无多轮 | 单轮 Ask | P2 再做；先稳定单轮 |

勾选：

- [ ] 演示前预热（warmup）
- [ ] 失败/超时/无命中友好文案
- [ ] （可选）改写策略对比实验
- [ ] （P2）多轮上下文

### 5. 工程与评测

| 问题 | 现状 | 优化方向 |
|------|------|----------|
| 缺评测集 | 主要靠手工点 | 20 条题：期望文档/关键词，跑 hit@k |
| 关键回归偏薄 | 有单测，缺「固定问句必中」 | 加 3～5 条 golden query 集成测试 |
| Chroma 客户端重复创建 | `get_chroma_store()` 每次 new | 进程内单例，减开销与锁风险 |
| chromadb 钉在 0.5 | 与新工具不兼容 | 可接受；文档写明版本，避免升级翻车 |

勾选：

- [ ] 小评测集 / hit@k 脚本
- [ ] golden query 集成测试
- [ ] ChromaStore 单例
- [ ] README 写明 chromadb 版本与已知限制

### RAG 优化排期（三刀）

**第 1 刀（效果立竿见影）**

1. 空命中 / 低分拒答  
2. 最终回答挂引用  
3. 固定 5 题演示语料调通  

**第 2 刀（证明你懂 RAG）**

4. 对外暴露 rank/score（不要在 `_public_hits` 里掐掉）  
5. 调试面板或至少 search 返回分项分数  
6. 开/关混合、Rerank 的对比记录  

**第 3 刀（工程可信）**

7. 索引健康检查 + FTS backfill 入口  
8. 小评测集 / golden 测试  
9. 预热与失败文案  

### RAG 过程中要深耕的

1. **召回漏斗取舍**：fetch / candidate / top_k、混合与精排何时有用——用自己的对比表说话  
2. **拒答与溯源**：空结果、低分、前端引用——「减幻觉」的实锤  
3. **一致性与降级**：四库不同步、FTS 挂了、LLM 挂了时系统怎么表现  

先不必深耕：换更大模型、上 GraphRAG、上多 Agent——在现有库规模下收益低。

**一句话**：差的不是「有没有混合检索」，而是 **拒答/引用、分数可观测、固定题集上的效果证明**。
