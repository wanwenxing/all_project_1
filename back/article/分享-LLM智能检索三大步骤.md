# LLM 智能检索分享：从向量命中到可对话回答

> 配套能力：`POST /api/docs/search`（传统向量检索）与 `POST /api/docs/ask`（LLM 智能检索）。  
> 编排代码：`app/rag/ask_graph.py`；业务 Prompt：`app/llm/ask_llm.py`。

---

## 1. 背景

个人知识库一期已经具备「存 + 搜」：

1. 本地 Markdown → 切分 chunk → Embedding（BGE）→ 写入 Chroma  
2. 用户输入关键字 / 问句 → 向量相似度检索 → 返回带分数、来源的片段列表  

对应接口是 `/api/docs/search`，前端「知识库检索」走这条链路。优点是**快、可控、每条都是原文**；但问法一绕就容易召不齐，结果也只是材料列表，用户还要自己拼答案，交互偏工具感。

---

## 2. 此次目标

在不改动向量库与 Embedding 的前提下，补齐 **LLM 智能检索**（`/api/docs/ask`），让知识库能「对话式回答问题」：

1. **问前**：大模型优化用户问题，降低问法敏感  
2. **检索中**：复用现有向量检索召回片段  
3. **答后**：大模型基于命中材料生成自然语言回答，并约束不编造  
4. **体验**：SSE 透出全过程，前端做成微信式气泡对话  

一句话区分两套能力：

- **传统向量检索**：「库里有哪些片段和这句话像？」  
- **LLM 智能检索**：「结合知识库，用自然语言把你的问题讲清楚。」  

二者是上下游，不是替代关系：智能检索中间仍调用同一套向量检索，只是前后各加一层大模型。

---

## 3. 总览：一条三步流水线

```mermaid
flowchart LR
  U[用户原问题] --> R[① 改写 rewrite]
  R --> V[② 检索 retrieve]
  V --> A[③ 生成 answer]
  A --> O[自然语言回答]
```

| 步骤 | 谁在干活 | 输入 | 输出 | 失败时 |
|------|----------|------|------|--------|
| ① 改写 | LLM | 用户原问题 | 更利于向量检索的精简问句 | 回退用原问题继续 |
| ② 检索 | Embedding + Chroma | 优化后问句（可加过滤条件） | Top-K 命中片段 | 整次中止，提示错误 |
| ③ 生成 | LLM | 原问题 + 优化问句 + hits | 流式自然语言回答 | 返回已生成部分并报错 |

编排用 **LangGraph** 固定为线性图：`rewrite → retrieve → answer`。  
过程通过 **SSE** 推给前端（优化中 / 检索完成 / 回答逐字出现），并写入 `ask_logs` 便于事后审计。

---

## 4. 三大关键步骤（重点）

### 4.1 ① 问题改写（Rewrite）——让检索「听得懂人话」

**要解决什么**  
向量检索吃的是「语义接近的短文本」。人说话经常带情绪、背景、口语，或一次抛出多个意图。直接拿原句去 Embedding，容易和日记里的书面表述对不齐。

**本步做什么**  
把原问题改写成：**更短、更聚焦、更贴近知识库表述习惯** 的中文问句。Prompt 约束「只输出问句本身」，温度偏低，减少发挥。

**例子（示意）**

| 用户原问题 | 改写后（示意） |
|------------|----------------|
| 「最近老觉得朋友之间的关系有点微妙，不知道该怎么相处」 | 「友情相处 / 朋友关系」 |
| 「职业迷茫和收支规划」 | 「职业迷茫 收支规划」 |

**和传统检索的关系**  
传统检索也可以让用户自己改关键字；智能检索把这一步自动化了，降低「会不会提问」的门槛。  
改写失败时 **fallback 原问题**，保证链路不断。

---

### 4.2 ② 向量检索（Retrieve）——和传统检索是同一套引擎

**要解决什么**  
从个人知识库里找出与问题最相关的原文片段，作为后续回答的**唯一事实来源**。

**本步做什么**  
走与「知识库检索」**完全同一套**向量召回流程：

1. 对（优化后的）问句做 Embedding  
2. 在 Chroma 里做相似度查询  
3. 可选按文件路径、标题、更新时间精确过滤  
4. 返回最相关的若干原文片段（含内容、标题、路径、分数等）

**关键认知**  
智能检索的「智能」**不是换了一种向量算法**，而是：

- 检索入口从「用户原句」变成「改写后的问句」  
- 检索出口从「直接展示给用户」变成「交给下一步生成」

没有命中材料时，第三步仍会跑，但 Prompt 要求模型明确说明「无法从知识库得出结论」，避免瞎编。

---

### 4.3 ③ 答案生成（Answer）——把材料变成可对话的结论

**要解决什么**  
用户要的是「帮我看看日记里怎么说的」，而不是「这里有 5 条 chunk，请自行阅读」。

**本步做什么**  
把 hits 格式化成带编号、标题、路径、相关度的材料块，连同「用户原问题」和「检索用问题」一起交给 LLM，流式生成回答。

约束很明确：

1. **只能依据检索材料**作答  
2. 材料不足时如实说明，**不要编造**  
3. 可用简洁中文；必要时文末列出来源标题或路径  

**和传统检索的关系**  
传统检索到此结束；智能检索多出这一层「带依据的复述与归纳」。  
生成质量高度依赖第二步命中质量——改写与检索仍是根基，LLM 不能凭空补知识库里没有的内容。

## 5. 对比：传统向量检索 vs LLM 智能检索

```mermaid
flowchart TB
  subgraph traditional [传统向量检索 /search]
    q1[用户关键字或问句] --> e1[Embedding]
    e1 --> c1[Chroma Top-K]
    c1 --> out1[片段列表 + score]
  end

  subgraph llm_ask [LLM 智能检索 /ask]
    q2[用户自然语言问题] --> rw[LLM 改写]
    rw --> e2[Embedding]
    e2 --> c2[Chroma Top-K]
    c2 --> an[LLM 基于 hits 生成]
    an --> out2[对话式回答 + 可展开片段]
  end
```

| 维度 | 传统向量检索 | LLM 智能检索 |
|------|--------------|--------------|
| 接口 | `POST /api/docs/search` | `POST /api/docs/ask` |
| 用户输入 | 关键字 / 短问句为主 | 口语化完整问题更自然 |
| 检索前 | 无（或用户自己改词） | LLM 改写问句 |
| 检索引擎 | BGE + Chroma | **同一套** BGE + Chroma |
| 检索后 | 直接返回 hits | LLM 综合 hits 生成回答 |
| 输出形态 | 结构化片段列表 | SSE 流式自然语言 + 过程提示 |
| 前端体验 | 列表 / 工具页 | 微信式左右气泡对话 |
| 可解释性 | 每条原文一目了然 | 回答可溯源；过程与 hits 可展开查看 |
| 延迟与成本 | 低（本地 Embedding + 向量库） | 更高（两次 LLM + 检索） |
| 幻觉风险 | 低（只展示原文） | 需靠 Prompt「禁止编造」+ 无材料声明来约束 |
| 适用场景 | 找原文、核对出处、调试召回 | 问答、总结、演示「知识库能说话」 |

**怎么选**

- 要找某一篇日记原文、调 Top-K / 过滤条件 → 用传统检索  
- 想快速得到「结合库的回答」、演示 RAG 闭环 → 用智能检索  
- 两者并存：智能检索内部复用传统检索，没有维护两套向量库

## 6. 一次完整交互长什么样

用户说：「友情相关的问题」

| 阶段 | 用户看到的（对话 UI） | 系统实际在做 |
|------|----------------------|--------------|
| 发送 | 右侧绿气泡：原问题 | 建立 SSE，启动 LangGraph |
| 改写 | 中间灰条：正在优化问题… → 已优化为：… | `rewrite` 节点流式改写 |
| 检索 | 中间灰条：正在检索… → 命中 N 条 | 用优化后问句做向量相似度召回 |
| 材料 | 左侧可折叠「相关知识片段」 | 展示 hits，供核对 |
| 回答 | 左侧白气泡逐字出现 | `answer` 节点流式生成 |
| 结束 | 气泡定稿；可选取消中途 abort | 写 `ask_logs` |

对比：若同一问题走传统检索，页面只会得到片段列表，没有改写提示，也没有综合回答。

---

## 7. 小结与可讨论问题

**小结**

1. 智能检索 = **改写 +（原有）向量检索 + 生成**，核心增益在两头的 LLM，中间检索引擎未换。  
2. 改写提升「问得准」，生成提升「答得好」；召回质量仍然决定上限。  
3. 传统检索适合找原文与调参；智能检索适合问答体验与演示闭环；产品上两者互补。

**讨论点**

1. 什么时候该跳过改写？（极短关键字、已带精确过滤时）  
2. 命中质量差时要不要自动二次检索？如何定义「差」？  
3. 向量检索出来的topK片段，准确度不是很高，如何优化？
