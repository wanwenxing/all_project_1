# 个人知识库 RAG 实现分享

## 背景与目标

### 背景

想自己用 Python 作为轻量后台，做一个前后端分离的项目。

后端侧重点是：结构清晰、本地可跑、方便持续加功能；前端用独立的 React 项目对接接口。整体更偏向个人可维护的小而完整工程，而不是一上来就上重型框架。

### 目标

1. **基础能力齐全**：包含最基本的登录与权限校验（注册 / 登录 / JWT / 改密失效等）。
2. **个人知识库**：把本地 Markdown 日记沉淀成可管理的知识库（上传、索引、增量更新）。
3. **简单 RAG 检索问答**：支持自然语言检索，召回相关片段并带来源，为后续接 LLM 生成答案打底。
4. **可扩展的作品底座**：后续想加的能力都可以集成进这个项目，方便做 demo 演示，也方便个人作品持续累积。

## 1. 当前已实现功能

| 模块 | 能力 |
|------|------|
| 用户鉴权 | 注册、登录、JWT、改密后旧 Token 失效、1 小时空闲滑动过期 |

当前阶段重点是 **RAG Phase 1**：

1. **存储**：本地文档 → 拆分 chunk → SQLite 元数据 + Chroma 向量

尚未包含：大模型最终生成答案（`/ask`）、语雀 API 同步（我的个人文档都在语雀上的，暂时是手动导出到本地进行的RAG存储）等。

## 4. 整体架构

### 4.1 知识库存储设计

入库链路：本地原文 → 解析 → 拆分 → 同时写入 SQLite（元数据 / chunk）与 Chroma（向量）。

```text
┌─────────────┐     ┌──────────────┐     ┌─────────────────────┐
│  docs/*.md  │ --> │ loader       │ --> │ ParsedDocument      │
│  原文       │     │ 解析元数据   │     │ 正文 + hash + 时间  │
└─────────────┘     └──────────────┘     └──────────┬──────────┘
                                                   │
                                                   ▼
                                         ┌─────────────────────┐
                                         │ splitter 拆分 chunk │
                                         └──────────┬──────────┘
                    ┌───────────────────────────────┼───────────────────────────────┐
                    ▼                               ▼                               ▼
           SQLite documents              SQLite document_chunks              Chroma diary_chunks
           文档级元数据                   chunk 文本 + chroma_id              向量 + 文本 + metadata
```

### 4.2 检索流程

```text
┌─────────────┐     ┌──────────────────┐     ┌─────────────────────┐
│ 用户 query  │ --> │ BGE embed_query  │ --> │ query_embedding     │
│ 自然语言问题 │     │ 问题向量化       │     │ 查询向量            │
└─────────────┘     └──────────────────┘     └──────────┬──────────┘
                                                       │
                          ┌────────────────────────────┼────────────────────────────┐
                          ▼                                                         ▼
                 ┌─────────────────┐                                      ┌─────────────────┐
                 │ 可选 where 过滤 │                                      │ Chroma query    │
                 │ 路径/标题/时间  │ ───────────────────────────────────► │ 向量相似度检索  │
                 └─────────────────┘                                      └────────┬────────┘
                                                                                   │
                                                                                   ▼
                                                                      ┌─────────────────────────┐
                                                                      │ hits                    │
                                                                      │ 文本片段 + 分数 + 来源  │
                                                                      └─────────────────────────┘
```

## 5. 知识库存储（详细）

### 5.1 存储目标

| 存储 | 存什么 | 用途 |
|------|--------|------|
| 本地 `docs/` | 原始 Markdown | 唯一内容源头 |
| SQLite `documents` | 文档级元数据 | 增量判断、状态、来源 |
| SQLite `document_chunks` | 拆分后的块文本 | 块档案、与向量对齐 |
| Chroma | chunk 向量 + 文本副本 + metadata | 语义检索 |

### 5.2 入库主流程

入口可以是：

- API：`POST /api/docs/index`
- CLI：`uv run python scripts/index_docs.py [--rebuild]`

#### 扫描范围：全量 vs 指定

入库时先决定「这次处理哪些文件」，有两种方式：

| 方式 | 怎么触发 | 做什么 |
|------|----------|--------|
| **全量扫描** | 不传 `path`，或跑 CLI 默认命令 | 扫描整个 `docs/`，对目录里每篇文档做增量判断；并清理「库里有记录、磁盘上已删掉」的旧索引 |
| **指定文件** | API 传 `path=docs/某篇.md` | 只处理这一篇，不扫全目录，也不做「删文件后的对账清理」 |

两种方式都可以再叠加 **是否强制重写**：

- **增量（默认）**：内容没变就跳过，省掉拆分和向量化时间  
- **强制重建**：全量时清空后重来（`--rebuild` / `rebuild=true`）；指定文件时则不管 hash 是否变化，都重写这一篇

#### 每次扫描在做什么（思路）

无论全量还是指定，对「要处理的每一篇」核心思路都一样：**以磁盘原文为唯一真相，用内容指纹判断要不要更新，更新时整篇替换，保证库和文件一致。**

#### 内容指纹是什么、为什么用

内容指纹（`content_hash`）可以理解成「这篇正文的数字摘要」：对当前正文做一次固定算法（SHA256）算出一串十六进制字符串。

设计思想很简单：

1. **比的是内容，不是文件名或修改时间**  
   文件改名、mtime 抖动都不该触发重索引；只有正文真的变了，才值得重新拆分和向量化（向量化相对更贵）。

2. **相同正文 → 相同指纹，不同正文 → 几乎必然不同指纹**  
   入库时把指纹和文档一起存进 SQLite；下次再扫到同一路径，把「现算的指纹」和「库里存的指纹」一比，就能判断有没有变化。

3. **用来做增量闸门，而不是当主键**  
   文档仍按路径（`source_path`）定位；指纹只负责回答「要不要重做这一篇」。强制重建时可以无视指纹，一律重写。

4. **粒度上以「整篇正文」为准**  
   跳过/更新的决策看的是文档级指纹。拆分后的每个 chunk 也会各自带一份文本指纹，方便对账和排查，但不单独驱动「要不要索引这篇」。

大致步骤：

1. **读原文、算指纹**  
   解析 Markdown，得到标题、正文、更新时间等元数据，并对正文算 `content_hash`（内容指纹）。

2. **决定跳过还是更新**  
   若库里已有这篇、指纹没变、且上次已成功入库 → 认为没有变化，直接跳过。  
   强制重建时则跳过这一判断，一律重写。

3. **先清旧再写新（整篇替换）**  
   一旦要更新，先删掉这篇在 SQLite / Chroma 里的旧块和旧向量，再按当前正文重新拆分、写入、向量化。  
   这样不会出现「旧 chunk 残留」或「半新半旧」的状态。

4. **拆分 → 落库 → 向量化**  
   正文按段落/长度拆成若干 chunk；块文本进 SQLite，向量进 Chroma，两边用同一套 id 对齐，并带上来源路径、标题等元数据，方便检索时过滤和溯源。

5. **标记完成**  
   全部写成功后，把该文档状态记为已索引，并保存最新指纹，供下次增量对比。

全量扫描还会多一步 **对账**：对比「目录里现在有哪些文件」和「库里还记着哪些路径」，把磁盘上已经不存在的文档从索引里清掉，避免检索命中幽灵内容。

### 5.3 拆分策略（splitter）

针对日记类短文本：

1. 按空行 `\n\n` 切成段落  
2. 短于 50 字的段落与下一段合并  
3. 超过 `chunk_size`（默认 300）再按长度切，并保留 `overlap`（默认 50）

### 5.4 拆分后的块长什么样（真实样例）

以 `docs/有意思的团建.md` 为例，原文大致是：

```markdown
今天去搓一顿豪气的烤肉店……

所以其实上班挺好的……

然后饭后听前辈讲职业迷茫和收支规划……

+ 收支不能太过单一
+ 希望获取资源的时候……
+ 多学习一些东西……

更新时间：2026年6月
```

索引后拆成 **3 个 chunk**（示意）：

#### Chunk 0（`chunk:1`）

```text
今天去搓一顿豪气的烤肉店，要是换我自己私下消费，我肯定是舍不得滴。

所以其实上班挺好的，至少有人会为自己的价值买单。
```

#### Chunk 1（`chunk:2`）

```text
然后饭后听前辈讲职业迷茫和收支规划，还蛮有意思，其实世界就是变化的，人之间的交往本质都是等价互换，人真的不用去惧怕变化，或许人生会有很多可能性呢。
```

#### Chunk 2（`chunk:3`）

```text
+ 收支不能太过单一
+ 希望获取资源的时候，想想自己能带给别人什么
+ 多学习一些东西，多利用一些场景社交其实是好事儿，至少可以换朋友圈
```

> `更新时间：2026年6月` 会在 loader 阶段抽成元数据，不进入正文 chunk。

### 5.5 SQL 中长什么样

**`documents`（文档级）示例：**

| id | source_path | title | chunk_count | index_status | updated_at |
|----|-------------|-------|-------------|--------------|------------|
| 1 | docs/有意思的团建.md | 有意思的团建 | 3 | indexed | 2026年6月 |

**`document_chunks`（块级）示例：**

| id | document_id | chunk_index | chroma_id | content（摘要） |
|----|-------------|-------------|-----------|-----------------|
| 1 | 1 | 0 | chunk:1 | 烤肉店……价值买单 |
| 2 | 1 | 1 | chunk:2 | 职业迷茫……可能性 |
| 3 | 1 | 2 | chunk:3 | 收支不能太过单一…… |

关联关系：`documents.id` ← `document_chunks.document_id`（一对多）。

### 5.6 Chroma 中长什么样

每条向量记录大致包含：

```json
{
  "id": "chunk:1",
  "document": "今天去搓一顿豪气的烤肉店……价值买单。",
  "embedding": [0.012, -0.034, "...共 1024 维"],
  "metadata": {
    "document_id": 1,
    "chunk_id": 1,
    "chunk_index": 0,
    "source_path": "docs/有意思的团建.md",
    "title": "有意思的团建",
    "updated_at": "2026年6月"
  }
}
```

说明：

- `id` = SQL 里的 `chroma_id`
- `document` = chunk 原文（不是整篇 md）
- `embedding` = BGE 向量
- `metadata` 用于检索时过滤、回显来源

## 6. 知识库向量检索（详细）

### 6.1 API 入口

```http
POST /api/docs/search
Authorization: Bearer <token>
Content-Type: application/json
```

请求体示例：

```json
{
  "query": "职业迷茫和收支规划",
  "top_k": 5,
  "source_path": "docs/有意思的团建.md",
  "title": "有意思的团建",
  "updated_at": "2026年6月"
}
```

字段说明：

| 字段 | 必填 | 含义 |
|------|------|------|
| `query` | 是 | 自然语言问题 / 关键词 |
| `top_k` | 否 | 返回条数，默认 5 |
| `source_path` | 否 | 按文件路径精确过滤 |
| `title` | 否 | 按标题精确过滤 |
| `updated_at` | 否 | 按更新时间标签精确过滤 |

### 6.2 背后转化链路

思路可以概括成：**问题向量化 →（可选）缩小检索范围 → 在向量库里找最近邻 → 把结果整理成可读字段。**

1. **接收用户请求**  
   至少要有自然语言问题 `query`；可选 `top_k` 控制返回条数，以及路径 / 标题 / 时间等精确过滤条件。

2. **把问题变成向量**  
   用与入库时同一套 BGE 模型，把 `query` 编成一条查询向量（本项目为 1024 维）。  
   检索和入库必须「同一套语义空间」，否则相似度没有意义。

3. **拼装可选过滤条件**  
   若传了 `source_path` / `title` / `updated_at`，把它们转成向量库能理解的精确匹配条件；多个条件同时存在时做「且」关系。  
   过滤发生在相似度排序之前，用来限定「在哪些文档的 chunk 里搜」。

4. **在向量库中检索**  
   用查询向量去 Chroma 里找最相近的若干 chunk（数量由 `top_k` 决定），同时带上上面的过滤条件（若有）。  
   库返回的是距离（越小越像）以及 chunk 文本、来源等元数据。

5. **整理成对外结果**  
   把距离转成更直观的分数（约等于 `1 - distance`），并把元数据展开成前端可用字段（路径、标题、chunk 序号等），形成 `hits` 列表返回。

### 6.3 转化后的中间格式

#### A. Query 向量

```python
# 概念示意（真实为 1024 维浮点）
query_embedding = [0.021, -0.015, 0.088, ...]
```

#### B. where 过滤（拼装后的示意）

无过滤：

```python
None
```

单条件：

```json
{"source_path": {"$eq": "docs/有意思的团建.md"}}
```

多条件：

```json
{
  "$and": [
    {"source_path": {"$eq": "docs/有意思的团建.md"}},
    {"title": {"$eq": "有意思的团建"}},
    {"updated_at": {"$eq": "2026年6月"}}
  ]
}
```

这就是传给 Chroma 的 metadata 过滤格式。

#### C. Chroma 原始返回（概念）

```json
{
  "ids": [["chunk:2", "chunk:1", "chunk:3"]],
  "documents": [["然后饭后听前辈讲职业迷茫……", "...", "..."]],
  "metadatas": [[{ "...": "..." }, { }, { }]],
  "distances": [[0.18, 0.31, 0.42]]
}
```

`distance` 为余弦距离，越小越相似；代码里转成：

```text
score ≈ max(0, 1 - distance)
```

### 6.4 最终返回给前端的内容

统一包在业务响应里：

```json
{
  "code": 0,
  "message": "检索完成",
  "data": {
    "query": "职业迷茫和收支规划",
    "total": 2,
    "hits": [
      {
        "chroma_id": "chunk:2",
        "content": "然后饭后听前辈讲职业迷茫和收支规划，还蛮有意思……",
        "distance": 0.18,
        "score": 0.82,
        "document_id": "1",
        "chunk_id": "2",
        "chunk_index": 1,
        "source_path": "docs/有意思的团建.md",
        "title": "有意思的团建",
        "updated_at": "2026年6月"
      }
    ]
  }
}
```

可以这样理解最终线索：

| 字段 | 告诉你什么 |
|------|------------|
| `content` | 命中的知识片段原文 |
| `score` / `distance` | 和问题有多像 |
| `source_path` / `title` | 来自哪篇日记 |
| `chunk_index` / `chroma_id` | 是第几块、向量库里哪条 |
| `updated_at` | 文档时间标签（若有） |

前端「知识库」页拿到 `hits` 后，即可展示「答案线索 + 来源引用」。若后续接 LLM，再把这些 `content` 拼成 prompt 生成自然语言回答。

## 7. 一张图串起来

```text

本地 md
  → loader（解析）
  → splitter（块）
  → SQL（documents / document_chunks）
```

## 9. 总结

本项目把个人日记做成了可检索知识库：

1. **存储**：段落优先拆分 → SQL 记档案 → BGE 向量化 → Chroma 存向量  
2. **检索**：问题向量化 + 可选 metadata 过滤 → 返回相似 chunk 及来源  

当前交付的是「能存、能搜、有来源」的 RAG 底座；下一步可自然扩展为「检索结果 + LLM 生成最终回答」。
