# 从 0 搭一套可用的个人知识库 RAG（实践一期）：FastAPI + Chroma + BGE

> 本文基于一个前后端分离的小项目实践（**个人知识库实践一期**）：把本地 Markdown 日记入库，支持上传、增量索引、向量检索 + 条件过滤。不堆概念，只讲我们落地时真正用到的链路和踩坑。

---

## 1. 我们要解决什么问题

个人日记、笔记越积越多，靠文件名搜索不够用。目标很明确：

1. 上传 `.md` / `.txt` 到服务端
2. 切块、向量化、写入向量库
3. 用自然语言关键词检索，并支持按文件路径、标题、时间过滤

一期先做到「能搜到相关片段」，问答大模型可以后续再接。

---

## 2. 技术选型（够用就好）

| 环节 | 选型 | 原因 |
|------|------|------|
| API | FastAPI | 异步友好，OpenAPI 开箱即用 |
| 元数据 | SQLite + SQLAlchemy | 轻量，记录文档/切块状态 |
| 向量库 | ChromaDB（本地持久化） | 零运维，适合个人项目 |
| Embedding | `BAAI/bge-large-zh-v1.5` | 中文检索表现稳定 |
| 前端 | React + Ant Design | 上传/索引/检索一个页面搞定 |

整体可以看成两条存储：

- **SQLite**：文档级信息（路径、hash、索引状态）+ chunk 级文本与 `chroma_id`
- **Chroma**：向量 + 少量 metadata（`source_path` / `title` / `updated_at` 等）

---

## 3. 整体链路

```text
上传文件 → docs/
    ↓
解析 Markdown（标题、更新时间、正文 hash）
    ↓
切块（段落优先，超长再滑窗）
    ↓
BGE 向量化 → 写入 Chroma
同时写入 SQLite（documents / document_chunks）
    ↓
检索：query → embed_query → Chroma.query(+ where 过滤)
```

对外三个核心接口：

- `POST /api/docs/upload`：保存文件
- `POST /api/docs/index?path=docs/xxx.md`：单文件增量索引
- `POST /api/docs/search`：向量检索 + 可选条件过滤

---

## 4. 切块怎么做

我们没有一上来上语义分块，先用规则切，稳定、好 debug：

1. 按空行 `\n\n` 切段落
2. 过短段落合并（避免碎块太多）
3. 超过 `chunk_size=300` 再按字符滑窗切，`overlap=50`

思路很朴素：**段落优先保语义，长度限制保检索粒度**。

后面如果要提升效果，可以演进到：

- Markdown 标题感知切分
- 小块检索 + 父块返回答案（parent-child）
- 相邻句 embedding 相似度断点（语义分块）

但对个人日记场景，规则切分通常已经够用。

---

## 5. 索引：为什么强调「单文件增量」

全量扫目录简单，但有两个麻烦：

1. 每次都跑一遍，慢
2. 稍不注意，删除逻辑可能误伤其他文件的向量

我们最终做成：

- 同文件 + 内容 hash 不变 → **跳过**
- 同文件内容变了 → **只删该文件的 chunks（SQL + 对应 chroma_id）再重建**
- 新文件 → **只新增，不碰别的文档**

删除 Chroma 时，优先用 SQL 里记录的 `chroma_id`（形如 `chunk:12`）精确删除，而不是只靠 metadata `where`。  
这点很重要：Chroma 的 where 过滤在类型不一致时不够可靠，曾出现「索引一个文件，别的文件向量被清掉」的问题。

---

## 6. 检索：向量 + 条件，不是字符串拼接

页面上用户输入：

- 关键字：`友情`
- 过滤：`source_path=docs/好的友情不亚于爱情.md`

后端并不是拼成一句 SQL/全文检索，而是拆成两路：

```text
关键字  → BGE embed_query → query_embeddings
过滤条件 → Chroma where（$eq / $and）
```

等价调用类似：

```python
collection.query(
    query_embeddings=[query_vec],
    n_results=5,
    where={
        "source_path": {"$eq": "docs/好的友情不亚于爱情.md"}
    },
)
```

含义是：

> 在满足 metadata 条件的子集里，找与问题向量最相近的 top_k 个 chunk。

另外 BGE 查询侧会加前缀：

`为这个句子生成表示以用于检索相关文章：`

保证 query 和入库 passage 在同一语义空间。

## 7. 工程上几个真实坑

### 7.1 模型加载把接口拖死

首次加载 `bge-large` 很重。如果开发时 uvicorn 热重载监视了 `.venv`，模型文件一动就重启，缓存反复失效，上传/检索都会表现为「很慢」。

做法：热重载只监视 `app/`；模型优先走本地缓存（项目 `data/models` 或本机 HF cache），避免每次联网。

### 7.2 上传慢，其实不是上传慢

上传本身只是写文件。真正卡住的，经常是旁边有一个正在跑的索引/下模型请求占满进程。  
把「上传」和「索引」拆开，体感会好很多。

### 7.3 单文件更新不能扫全库删

增量更新必须按 `document_id` / `chroma_id` 精确清理，否则会出现「更新 A，B 消失」。

## 8. 一期效果与后期优化目标

一期已经能做到：

- 本地知识库存取
- 单文件增量索引
- 语义检索 + 路径/标题/时间过滤
- 前端可视化操作

### 后期优化目标

**1. 根据检索效果反推、优化文本切块**

一期用的是「空行切段 + 短段合并 + 超长滑窗」，稳定但偏粗糙。后续会结合检索命中率/排名称，对比市面上更常见的切块方式，按需升级，例如：

- **结构感知**：按 Markdown 标题 / 段落递归切（LangChain、LlamaIndex 一类）
- **句子级 + overlap**：先分句再拼到长度上限，避免句中硬切
- **语义分块**：相邻句 embedding 相似度低谷处切开
- **Parent-child**：小块入向量库负责定位，父块原文负责给模型看

原则是：**用评测看哪种切法对「搜得准」更有帮助**，而不是一次性换成最复杂的方案。

**2. 检索之后接入 LLM，做成语义化问答**

现在返回的是相关 chunk 列表。下一步在检索结果之上接大模型：

```text
用户问题 → 向量检索(+过滤) → 组装上下文 → LLM 生成答案（可带来源引用）
```

把「搜片段」升级成「基于知识库的问答」，并约束模型只依据检索内容作答，减少幻觉。

其余可并行考虑：混合检索（向量 + 关键词）/ Rerank、小评测集回归等。

---

## 9. 小结

个人知识库 RAG 不必一开始就上很重的框架。把这四件事做扎实，就已经很好用了：

1. **切得合理**（段落 + 长度限制）
2. **嵌得一致**（同一 embedding，query 前缀正确）
3. **更新可控**（单文件增量，精确删除）
4. **检索可过滤**（向量召回 + metadata 条件）

其余优化，等真正遇到「搜不准 / 答不全」再加，通常比一开始堆组件更划算。
